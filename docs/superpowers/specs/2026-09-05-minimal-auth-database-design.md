# 极简登录、数据库与三端权限设计

- 日期：2026-09-05
- 状态：用户已确认
- 项目：兵工铸魂 · 智绘“易”学

## 1. 背景

当前项目使用 React + Vite，部署在 Vercel。现有“登录页”仅供用户选择学生、教师或学校管理员身份，登录后仍可切换三个端；学生、教师和学校端的数据主要来自浏览器 `localStorage` 与模拟数据，不能形成真实的多用户数据隔离。

本次改造面向装备工程学院约 300 名学生的短期试用，同时保留将来扩展到全校的可能。

## 2. 目标

1. 增加真实账号密码登录。
2. 登录后由数据库中的角色自动进入学生端、教师端或管理员端。
3. 将学生测评、画像和学习记录保存到云数据库。
4. 在界面、数据库和 AI 接口三层校验权限。
5. 保持功能简单，优先快速、稳定上线。

## 3. 不做的功能

本期明确不做：

- 用户自行注册。
- 强制修改密码。
- 找回密码页面。
- 自定义连续输错锁定。
- 教师注册与审核。
- 多班级配置页面。
- 应用内账号管理页面。
- 保存 AI 对话内容、模型回答或上传图片。
- 迁移现有 `localStorage` 演示数据。

Supabase 自身提供的基础安全限制不属于本项目新增功能，保持平台默认设置。

## 4. 总体架构

保留现有 React + Vite + Vercel 架构，新增 Supabase：

- Supabase Auth：账号认证和会话管理。
- Supabase PostgreSQL：保存用户资料、测评和活动记录。
- Supabase Row Level Security（RLS）：在数据库层限制每种角色可读写的数据。
- Vercel Serverless Functions：继续代理 DeepSeek 和通义千问请求，并在调用模型前验证 Supabase 登录令牌。

前端使用 Supabase 的公开 URL 和匿名密钥；管理员密钥只允许放在 Vercel 环境变量或本地导入脚本中，不能进入前端代码或 GitHub。

## 5. 账号方案

### 学生

- 登录账号：学号。
- 初始密码：学号。
- 姓名：只用于登录后展示，不参与认证。
- 约 300 个账号通过一次性本地脚本批量导入。
- 输入名单只需要 `student_no,name` 两列。
- 不收集、保存完整身份证号码或身份证后六位。

Supabase Auth 内部使用不可见的占位邮箱映射学号，用户界面始终只显示“学号”和“密码”。账号由管理员接口预创建，不发送邮件验证。

“账号与密码相同”仅适用于本次院内短期试用。若存储更敏感的数据、开放公网长期使用或推广到全校，必须另行升级密码方案。

### 教师与管理员

- 预创建 1 个教师账号和 1 个管理员账号。
- 两个账号使用不同、难猜的账号和密码。
- 不开放教师或管理员注册。
- 如需新增或停用账号，暂时通过 Supabase 控制台或本地导入脚本完成，不开发管理页面。

## 6. 角色与权限

系统只有三种角色：`student`、`teacher`、`admin`。

| 身份 | 可见范围 | 可写范围 |
| --- | --- | --- |
| 学生 | 自己的资料、测评和学习记录 | 可提交自己的测评和学习记录 |
| 教师 | 当前试点组全部约 300 名学生的资料、测评和学习统计 | 不可修改学生测评结果 |
| 管理员 | 全部学生详情、全部测评记录和全局汇总看板 | 不可修改学生测评结果 |

当前名单没有班级字段，因此所有学生统一属于“装备工程学院试点组”，唯一教师账号绑定该试点组。以后获得真实班级数据时，再增加班级字段和教师范围映射，不影响已有账号与记录。

学生提交的测评采用追加记录方式保存，历史结果不允许在客户端更新或删除。管理员可自由查看所有数据，但不能篡改学生测评结果。

## 7. 数据表

本期只建立三张业务表。

### 7.1 `profiles`

保存登录用户的业务资料：

- `id`：对应 Supabase Auth 用户 ID。
- `login_id`：学号或教师、管理员账号，唯一。
- `name`：姓名或显示名称。
- `role`：`student`、`teacher`、`admin`。
- `group_name`：当前固定为“装备工程学院试点组”。
- `is_active`：账号是否启用。
- `created_at`：创建时间。

角色、账号状态不能由普通前端用户自行修改。

### 7.2 `assessment_results`

保存学生每次测评结果：

- `id`：记录 ID。
- `user_id`：学生用户 ID。
- `scores`：八维画像分数。
- `profile_type`：画像类型。
- `created_at`：完成时间。

每次完成测评新增一条记录，不覆盖历史记录。

### 7.3 `activity_records`

统一保存案例学习、每日问题和 AI 使用统计：

- `id`：记录 ID。
- `user_id`：用户 ID。
- `event_type`：案例学习、每日问题、DeepSeek 调用或 Qwen 调用。
- `reference_id`：案例等业务对象标识，可为空。
- `success`：调用或操作是否成功，可为空。
- `created_at`：发生时间。

AI 记录只保存用户、调用类型、时间和是否成功，不保存提问、回答、图片或图片识别结果。

## 8. 登录与页面流程

1. 用户在登录页输入账号和密码。
2. 前端将账号转换成内部认证标识，调用 Supabase Auth。
3. 登录成功后读取 `profiles.role`。
4. `student` 只渲染学生端，`teacher` 只渲染教师端，`admin` 只渲染学校管理员端。
5. 移除当前登录页的身份选择卡片和登录后的三端切换标签。
6. 当前登录页上的拍照识别入口移到学生登录后的页面，避免未登录调用 Qwen。
7. 顶栏只显示当前用户名称、角色和退出按钮。
8. 刷新页面时恢复有效会话；退出后清除会话并返回登录页。

前端隐藏页面只改善体验，真实权限由 RLS 和服务端令牌校验保证。即使手动修改前端代码或请求参数，也不能越权读取数据。

## 9. 业务数据流

### 学生测评

学生完成测评后，将八维得分和画像类型写入 `assessment_results`。学生端只查询自己的历史记录。

### 教师端

教师端查询试点组全部学生的资料与测评记录，用真实数据库结果替换当前 `localStorage` 和模拟学生数据。教师只有读取权限。

### 管理员端

管理员端读取全部学生详情、测评历史和活动记录，并在前端计算或通过数据库查询生成汇总看板。管理员不能修改测评记录。

### AI 接口

前端调用 `/api/deepseek` 或 `/api/qwen-vl` 时携带 Supabase Access Token。Vercel 函数先验证令牌和账号状态，验证成功才调用模型；服务端固定允许使用的模型，并限制请求体大小和最大输出 Token，不直接信任前端传入的模型及额度参数。成功或失败后只写入一条最小化使用记录，未登录请求返回 401。学生只能写入自己的普通学习事件，AI 调用记录由 Vercel 函数写入，避免客户端伪造调用统计。

## 10. 错误处理

- 账号或密码错误：统一提示“账号或密码错误”，不暴露账号是否存在。
- 账号已停用：拒绝进入系统。
- 登录成功但无有效角色：拒绝进入任何端。
- 数据库或网络暂时不可用：保留页面并提示稍后重试。
- AI 接口未登录：返回 401。
- AI 服务失败：显示现有友好提示，并记录失败次数，不保存请求内容。

## 11. 验收标准

1. 学生使用学号和相同密码能够登录，且只能进入学生端。
2. 两名不同学生不能互相读取测评或学习记录。
3. 教师账号可查看试点组全部学生，但无法修改测评记录。
4. 管理员账号可查看每名学生详情和全部汇总，但无法修改测评记录。
5. 修改前端状态、地址或请求参数不能绕过数据库权限。
6. 未登录用户不能调用 DeepSeek 和 Qwen 接口。
7. 学生数据在换设备或清理浏览器后仍可恢复。
8. 数据库不保存 AI 对话、回答和上传图片。
9. 现有 `localStorage` 演示数据不会进入正式数据库。
10. 项目构建、现有学生测评流程和 AI 功能保持可用。

## 12. 后续扩展边界

若推广到全校，再单独设计以下功能，不纳入本期：

- 学院与班级表。
- 多教师账号及负责范围。
- 学校统一身份认证或易班认证。
- 更安全的初始密码、首次改密和密码找回。
- 管理员账号管理页面。
- 审计日志和更细粒度的数据授权。
